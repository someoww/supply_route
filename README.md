# Bangladesh supply-route risk: a causal simulator and a dispatch-time model

Synthetic district-day data for 31 districts, generated by an explicit structural causal model (SCM). A gradient-boosted model predicts route condition from what is known at dispatch. A causal module estimates what would change under an intervention (strike, state intervention, diesel price, rain, cold chain) and checks each estimate against the simulator's own ground truth.

Everything is synthetic. The coefficients encode assumptions, not measurements, so the results show that the methods work on this world, not what Bangladesh's supply chains look like.

## Files

| File | Role |
|---|---|
| `data_generator.py` | The SCM. Each node declares its parents and its equation; `simulate(do=...)` returns exact counterfactuals |
| `train.py` | Time-ordered training and evaluation on dispatch-time features |
| `predict.py` | Scores CSV or JSON input with a saved bundle |
| `causal.py` | Effect estimation versus the simulator's truth |
| `requirements.txt` | numpy, pandas, scipy, scikit-learn (1.4 or newer) |

## Setup

python3 -m venv .venv

## Usage

### 1. Generate data

```bash
python3 data_generator.py                                   # 3000 days x 31 districts = 93,000 rows -> data/routes.csv
python3 data_generator.py --days 1000                       # smaller panel, 31,000 rows
python3 data_generator.py --days 5000 --seed 7              # larger panel, different random world
python3 data_generator.py --start 2020-01-01                # shift the calendar start
python3 data_generator.py --days 3000 --out data/other.csv  # custom output path
```

| Flag | Default | Meaning |
|---|---|---|
| `--days` | 3000 | Days per district. Rows = days x 31 |
| `--seed` | 42 | Random seed. Same seed, same file |
| `--start` | 2016-01-01 | First date of the panel |
| `--out` | data/routes.csv | Output CSV; the folder is created if missing |

### 2. Train

```bash
python3 train.py                                            # condition_class, defaults
python3 train.py --target condition_score --model-out models/score.bin
python3 train.py --target delay_hours --model-out models/delay.bin
python3 train.py --data data/other.csv --model-out models/other.bin
python3 train.py --folds 6                                  # more cross-validation windows
python3 train.py --holdout 0.3                              # hold out the newest 30% of days
python3 train.py --data data/other.csv --target delay_hours --folds 3 --holdout 0.25 --model-out models/delay_other.bin
```

| Flag | Default | Meaning |
|---|---|---|
| `--data` | data/routes.csv | Input CSV from the generator (or any file with the same columns) |
| `--target` | condition_class | `condition_class`, `condition_score` or `delay_hours` |
| `--model-out` | models/model.bin | Where the bundle is written; the folder is created if missing |
| `--folds` | 4 | Expanding-window cross-validation folds |
| `--holdout` | 0.2 | Newest fraction of days kept for the final test |

The target picks the task: `condition_class` is classification, the other two are regression. Output is a JSON summary with cross-validation mean ± std and holdout metrics. Training the three targets as separate runs is the only way to get all three; each bundle holds one model.

### 3. Predict

The input is a CSV file, a JSON file, or a JSON string typed on the command line. Each row needs the dispatch-time features listed in the bundle (the 42 non-outcome columns of the generator's CSV).

```bash
python3 predict.py data/routes.csv                          # first 20 predictions printed
python3 predict.py data/routes.csv --out preds.csv          # all predictions to CSV
python3 predict.py data/routes.csv --out preds.json         # all predictions to JSON
python3 predict.py data/routes.csv --model models/score.bin # a different bundle
python3 predict.py request.json                             # JSON file
python3 predict.py '{"flood_index": 0.8, "strike": 1}'      # one inline record
python3 predict.py '[{"flood_index": 0.8}, {"flood_index": 0.1}]'                # inline list
python3 predict.py '{"instances": [{"flood_index": 0.8}, {"flood_index": 0.1}]}' # wrapped list
```

A JSON file or string can be a single object, a list of objects, or `{"instances": [...]}`. Nested objects are flattened with dots.

For `condition_class` the output has `prediction` (0, 1, 2), `label` (normal, degraded, critical) and one probability column per class. Regression bundles return `prediction` only.

Features missing from the input are treated as unknown and a warning names them. The more that are missing, the less the output means. If none match, the script exits.

| Flag | Default | Meaning |
|---|---|---|
| `input` | required | CSV path, JSON path, or JSON string |
| `--model` | models/model.bin | Bundle to load |
| `--out` | none | `.csv` or `.json`; without it the first 20 rows are printed |

### 4. Causal effects

```bash
python3 causal.py                                           # 2000 simulated days, seed 42
python3 causal.py --days 4000                               # more data, tighter estimates
python3 causal.py --seed 11                                 # different random world
python3 causal.py --days 3000 --seed 11
```

`causal.py` simulates its own data and does not read the CSV. It runs for a few minutes at larger `--days`, since it re-simulates the world under each intervention.

### 5. From Python

```python
from data_generator import simulate
from predict import load, predict
from causal import run

df = simulate(days=1000, seed=3)                          # the same frame the CSV holds
bundle = load("models/model.bin")
print(predict(bundle, df).head())

# what if no strikes had happened, for these exact days and districts?
calm = simulate(days=1000, seed=3, do={"strike": 0})
print((calm.condition_score - df.condition_score).mean())

# a continuous intervention: diesel 10 BDT/litre dearer
dear = simulate(days=1000, seed=3, do={"fuel_bdt": lambda x: x + 10})

print(run(days=1500, seed=5))                              # the table in the next section
```

`do` takes a constant or a function of the node's natural values. Everything downstream responds; everything upstream stays put.

## The causal model

Nodes are generated in topological order, and each draws from its own random stream. Roughly:

```
war_risk -> fuel_usd, shipping_disruption -> forex_pressure -> fuel_bdt, input_shock
month -> monsoon -> rain_mm -> river_m -> flood_index -> alert_level -> panic -> tcb, hoarding
unrest -> strike, curfew, extortion, internet_outage -> panic
strike, curfew, fuel_bdt -> truck_avail;  flood, strike -> bridge_congestion -> speed_kmh
(transit)  checkpost_h, ferry_wait_h -> travel_h -> delay_hours -> spoilage_pct, shortfall -> condition_score -> condition_class
```

- **Confounding is built in.** Unrest drives strikes, extortion and hoarding together. Panic and alerts trigger the state intervention (`tcb`) and also worsen shortages. Naive comparisons are therefore biased.
- **Geography is fixed per district** (density, elevation, route length, coastal and ferry dependence); product traits come from the product drawn per shipment.
- **Persistence.** Weather, unrest and macro shocks are AR(1) series, national or per district, so adjacent days resemble each other.
- **Same-day edges only.** There are no lagged causal effects, so every effect below is contemporaneous.
- **Outcomes are realised in transit** (`checkpost_h`, `ferry_wait_h`, `travel_h`, `delay_hours`, `spoilage_pct`, `shortfall`, `condition_*`). They are listed in `REALIZED` and kept out of every predictor.

`simulate(days, seed, do={"strike": 0})` replaces a node and lets its descendants respond with the same noise, so the difference between two runs is the true effect for the same units.

## Prediction

The model sees the 42 dispatch-time columns, with no identifiers. Geography and product traits already carry district and product identity.

- **Targets:** `condition_class` (0 normal, 1 degraded, 2 critical, from score cutoffs 75 and 50), `condition_score` (0 to 100) or `delay_hours`.
- **Validation:** the newest 20% of days are held out, with a 30-day buffer before them. Cross-validation uses expanding windows with the same buffer, so autocorrelated weather cannot leak across the boundary.
- **Boosting rounds** come from the newest 15% of each training window, not a random slice, then the model is refit on all of it.
- **Metrics:** macro-F1, log loss and per-class recall, because the critical class is rare. Regression reports MAE, RMSE and R².
- Thresholding the `condition_score` regression at 75 and 50 usually matches or beats the direct classifier on macro-F1 and critical recall, since it keeps the ordering of the classes. Compare both on your own seed.
- `model.bin` is a pickle. Load only bundles you trained.

## Causal estimates

`causal.py` compares four numbers per question (condition score is 0 to 100, higher is better):

| Question | Outcome | Oracle | Naive | Backdoor | All features |
|---|---|---|---|---|---|
| Transport strike on vs off | score | -24.2 | -27.2 | -23.4 | -0.2 |
| State intervention on vs off | shortfall | -0.138 | -0.051 | -0.137 | -0.088 |
| Diesel +10 BDT/litre | score | -1.6 | -5.8 | -1.9 | -0.3 |
| Rain +20 mm | score | -6.5 | -7.5 | -6.3 | -0.4 |
| Cold chain +0.1 | spoilage % | -0.58 | -1.76 | -0.51 | -0.55 |

- **Oracle:** re-simulation under `do(T)`.
- **Naive:** difference in means between treated and untreated rows. For continuous treatments, rows above and below the median.
- **Backdoor:** g-formula. An outcome model uses the treatment and its direct causes (its parents in the SCM), then averages the contrast over the observed rows. The `se` column in the full output comes from five time blocks.
- **All features:** the same g-formula, adjusting for every dispatch-time column. This is what flipping one input in the predictive model amounts to.

Reading it:

- Backdoor adjustment lands within about one or two standard errors of the oracle. Naive differences are off by up to 3x (diesel, cold chain) and can understate an effect (intervention).
- A predictive model is the wrong tool for what-if questions. Flipping `strike` inside it moves the score by almost nothing, because truck availability, congestion and speed, the channels through which a strike acts, stay fixed. Adjusting for mediators removes the effect you want.
- The parent set is a valid adjustment set only because the graph is known. On real data it is an assumption you have to defend.
- Effects are population averages. Strikes, floods and interventions hit rows unevenly, and estimates for rare treatments (strikes are about 2% of days) lean on regularisation and shrink a little toward zero.
- National series (`fuel_usd`, `war_risk`) have few independent episodes, so the effects of national shocks are poorly identified from one history. That is why the fuel question uses the local price, which also varies by row.

## Limits

- Simulated coefficients, not estimates. Replace the equations with data and the graph with a defended one before reading anything into the numbers.
- No spatial spillover between districts, no route network, no lagged effects.
- One product per row and one route per district.
- Class balance is roughly 75 / 21 / 4 percent (normal, degraded, critical) with strong monsoon seasonality; it shifts with the seed and with any change to the equations.
